================================================================================
  ANÁLISIS COMPRENSIVO DE FALLAS: LÓGICA, SISTEMA, SEGURIDAD Y DISEÑO HUMANO
                     SISTEMA SGA-CANTV - VERSIÓN 2026/06
================================================================================

Este documento detalla minuciosamente todos los fallos ocultos, fallas lógicas, 
vulnerabilidades de seguridad, problemas de experiencia de usuario (UX) e 
inconsistencias estructurales comunes en desarrollos asistidos por Inteligencia 
Artificial dentro de la aplicación actual. 

Aunque el sistema es funcional y visualmente atractivo, un análisis de 
ingeniería de software profunda revela debilidades críticas en el diseño de 
la arquitectura que el administrador y los usuarios finales enfrentarían tarde 
o temprano sin saberlo.

1. DESFASES DE SINCRONIZACIÓN EN EDICIÓN DE PERFILES (Firebase Web SDK vs Auth)
================================================================================
* Dónde ocurre: `src/App.tsx` -> `handleEditTechnician` (Líneas 1227-1326)
* Tipo de falla: Limitación Lógica de SDK / Falso Feedback visual.

* Detalle del problema:
  Cuando un administrador edita la información de un miembro del personal 
  (técnico, supervisor o administrador), se actualizan correctamente las 
  colecciones de Firestore `technicians` y `users`. Sin embargo, si el 
  administrador edita el correo institucional (email) o la contraseña:
  1. El Web SDK de Firebase prohíbe de forma estricta que una sesión cambie la 
     cuenta de autenticación de otro usuario por motivos de seguridad.
  2. Como resultado, el correo de Autenticación de Firebase (el que sirve para 
     hacer login) permanece inalterado, mientras que el perfil de base de datos 
     muestra el nuevo correo. Esto rompe la coherencia: el usuario ya no puede 
     conectarse con su nuevo correo y si escribe el viejo sufrirá un desfase 
     de identidad en su Panel.
  3. Para las contraseñas, la I.A. parchó esto enviando un correo de 
     restablecimiento ("sendPasswordResetEmail") de forma unilateral si se digita 
     algo en el campo "contraseña" de edición, y saltando un patch-alert. Esto 
     es un parche de interfaz muy incómodo (UX confusa): el formulario invita al 
     administrador a escribir una clave, pero el sistema realmente la descarta 
     detrás de escena y manda un enlace genérico.

* Impacto Humano/Diseño: 
  Soporte técnico recibirá constantes quejas de que "no pueden loguearse tras 
  el cambio de datos de recursos humanos".

2. BRECHAS DE SEGURIDAD EN LA ELIMINACIÓN DE PERSONAL (Cuentas Huérfanas con Acceso)
================================================================================
* Dónde ocurre: `src/App.tsx` -> `handleDelete` (Líneas 1328-1407)
* Tipo de falla: Brecha Crítica de Seguridad / Lógica Incompleta.

* Detalle del problema:
  El sistema ofrece dos tipos de borrado para el personal: eliminación lógica 
  (enviar a la papelera el documento de `technicians`) y eliminación física 
  (borrar del todo usando `deleteDoc` sobre la ID en `technicians`).
  1. El fallo reside en que en NINGUNO de los dos flujos se desactivan ni se 
     borran las credenciales del usuario en Firebase Authentication, ni se 
     vacia su coincidencia en la colección global `users`.
  2. Un empleado que ha sido despedido o dado de baja (bien sea de forma lógica 
     o permanente en la interfaz) conserva al 100% sus credenciales activas del 
     sistema de login. 
  3. Podrá seguir iniciando sesión en el SGA-CANTV desde cualquier dispositivo, 
     y aunque su menú o tabs no carguen datos de "technician" por no encontrarse 
     el enlace, tendrá un Token válido y podrá realizar peticiones que no pasen 
     por validación de existencia en la colección secundaria.

* Impacto Humano/Diseño: 
  Ex-tecnicós o ex-supervisores disgustados conservan el control de sus cuentas, 
  pudiendo acceder a paneles confidenciales del sistema de transmisión y datos 
  en la empresa estatal.

3. INESTABILIDAD DE REGISTROS MÚLTIPLES (Uso de Secondary Firebase app en Cliente)
================================================================================
* Dónde ocurre: `src/App.tsx` -> `handleAddTechnician` (Líneas 1133-1224)
* Tipo de falla: Anti-patrón de Concurrencia de Estado en el Navegador.

* Detalle del problema:
  Para registrar un nuevo perfil de técnico sin cerrar de forma forzosa la 
  sesión activa del administrador en el navegador, el código crea una instancia 
  virtual de Firebase App llamada "SecondaryRegistration" y un Authentication 
  secundario en el navegador del cliente. 
  1. Si bien funciona para creaciones esporádicas, esta técnica está totalmente 
     desaconsejada en producción web debido a que los navegadores modernos (que 
     usan un pool único de cookies y storage para Firebase) colisionan o 
     sufren demoras de estado.
  2. Si el administrador registra 3 perfiles seguidos rápidamente, la inicialización 
     del App secundario puede lanzar errores de "App already exists" o heredar 
     e invalidar el token de sesión activa del Administrador (Cerrándole la 
     sesión principal sin previo aviso).
  3. Además, si el correo ingresado tiene problemas de formato o la red se corta 
     en medio, el SignOut secundario podría no ejecutarse de forma limpia, dejando 
     la sesión secundaria interceptando peticiones del sistema.

* Impacto Humano/Diseño: 
  Es un hack cliente-único típico de código I.A. que esquiva levantar un servidor 
  Backend formal o usar Firebase Admin SDK SDK, comprometiendo la estabilidad.

4. RIGIDEZ EXTREMA DE VALIDACIONES (Fallo de Empatía y Lógica Humana)
================================================================================
* Dónde ocurre: `src/modules/technicians/components/TechnicianForm.tsx` (Líneas 70-130)
* Tipo de falla: Rigidez UX / Falta de adaptabilidad real.

* Detalle del problema:
  La I.A. ha implementado una validación sintáctica extremadamente inflexible, 
  perdiendo de vista la realidad laboral cotidiana:
  1. Validación de Celular (`/^\d{4}-\d{7}$/`): Exige estrictamente el formato 
     `0414-1234567`. Si un supervisor digita un número sin guion (ej. `04141234567`), 
     usa espacios (`0414 1234567`), incluye paréntesis, código internacional 
     (ej. `+58414...`) o números fijos de oficina CANTV, la interfaz deniega 
     salvar el perfil mostrandose hostil con el operador.
  2. Validación de Especialidad y Departamento (`/^[a-zA-ZáéíóúÁÉÍÓÚñÑüÜ\s]+$/`): 
     Prohíbe caracteres numéricos, guiones o barras. Si se quiere asociar a 
     un empleado al departamento "DATOS 2", "ENERGÍA SUR - TRANSMISIÓN II" o 
     colocar el cargo "Soporte (Nivel 3)", el formulario explotará indicando 
     que dichos campos solo admiten texto plano estricto.
  3. Campos de Dotación Opcionales pero con validaciones ocultas: Se puede obviar 
     escribir tallas, pero si se escribe algo sin ser mayúscula o en formatos que 
     la I.A. no previó, el formulario se bloquea.
  4. Fechas e Históricos Obligatorios: `fechaNacimiento` y `fechaIngreso` son 
     100% obligatorias para poder guardar. En cuadrillas antiguas, es habitual 
     que no se disponga del día de nacimiento o ingreso exacto de un técnico 
     contratado hace 15 años en el primer registro, bloqueando la carga administrativa 
     de su ficha temporalmente.

* Impacto Humano/Diseño: 
  El usuario final siente frustración absoluta ante una interfaz "tirana" que no 
  le permite resolver imprevistos comunes de digitación.

5. INCONSISTENCIAS SEMÁNTICAS Y BILINGÜISMO DE ESQUEMAS (Lógica de Base de Datos vs UI)
================================================================================
* Dónde ocurre: `src/types.ts` y todos los componentes de listado (Excel y Management).
* Tipo de falla: Deuda Técnica Estructural / Discordancia Idiomática.

* Detalle del problema:
  A nivel cosmético, el sistema usa títulos humanos y unificados ("Cédula" y "P00"). 
  Sin embargo, el back-end y el tipado de TypeScript sufren del fenómeno del 
  "Frankenstein semántico", herencia de parches múltiples ejecutados por I.A.:
  1. En el backend se llama `employeeId`, en la interfaz vieja `POO`, en el Excel 
     `P00 (CARNET)`, en el JSON de Firebase `carnet` o `employeeId`.
  2. En el backend la cédula es `idCard`, en el Excel `cedula`, y en el modal `Cédula de Identidad`.
  3. Los roles manejan niveles cruzados: en un lugar es `'admin' | 'supervisor' | 'tecnico'` 
     y en el modal de registro se expone y digita "TÉCNICO", "SUPERVISOR", lo que 
     obliga a normalizaciones manuales en cada función (`normalizedRole`) para 
     evitar estropear las reglas de autenticación basadas en strings exactos.

* Impacto Humano/Diseño: 
  Complejiza enormemente la mantenibilidad futura por programadores humanos. 
  Un ligero cambio de idioma en una clave del lado cliente puede colapsar el 
  filtrado o renderizado de datos históricos de nómina o labores de viáticos.

6. INEXISTENCIA DE TRANSACCIONES (Riesgo de Corrupción de Datos Concurrente)
================================================================================
* Dónde ocurre: `src/App.tsx` -> `handleAddTechnician` y `handleEditTechnician`
* Tipo de falla: Falla de Integridad Referencial de Base de Datos.

* Detalle del problema:
  La lógica de escritura escribe 4 veces seguidas de manera asíncrona pero sin 
  utilizar transacciones atómicas (`runTransaction` de Firestore). Por ejemplo, 
  al agregar un técnico:
  - Paso 1: Crea el Auth en Firebase con app secundaria.
  - Paso 2: Hace `addDoc` en la colección `technicians`.
  - Paso 3: Hace `setDoc` en la colección `users` para el perfil coincidente.
  - Paso 4: Hace `addDoc` en `notifications` para reflejar el evento.
  
  Si la conexión del operador falla repentinamente en el Paso 2 o Paso 3 (o si 
  la pestaña se cierra durante el proceso):
  1. La cuenta de Auth habrá quedado creada en Firebase.
  2. Pero la colección `technicians` o la colección `users` no se actualiza.
  3. Esto origina un perfil huérfano e inválido. La próxima vez que este técnico 
     intente ingresar de forma oficial usando su contraseña y correo reales, 
     el sistema lanzará un crash (`Cannot read properties of undefined`) porque 
     el Dashboard esperará un documento de Firestore asociado a su UID que 
     simplemente nunca existió o se grabó a medias.

* Impacto Humano/Diseño: 
  El sistema se vuelve inestable bajo conexiones lentas de telefonía móvil 
  o redes internas administrativas congestionadas.

7. COMPORTAMIENTOS INESTABLES Y PERFORMANCE EN RECHARTS (Maquetación Fluida vs Lienzo)
================================================================================
* Dónde ocurre: `src/modules/dashboard/components/Dashboard.tsx`
* Tipo de falla: Inestabilidad de Pintado en el Canvas / Overflows de UI.

* Detalle del problema:
  El gráfico de dona de distribución de trabajos utiliza `ResponsiveContainer` de 
  Recharts. Sin embargo, Recharts tiene una limitación conocida de rendimiento y 
  de lógica que hace que requiera un padre con ancho y altura constantes o relativos 
  pero no asíncronos:
  1. Al estar anidado dentro de arrays de flex y grids complejos de Tailwind en 
     el Dashboard, la dona puede sufrir el "bucle de recalculo infinito" de 
     dimensiones si el usuario minimiza la ventana, colapsando el rendimiento 
     del JavaScript del navegador (100% de uso de CPU).
  2. El Tooltip flotante con wrapperStyle de altísimo z-index (`zIndex: 100`) 
     es una solución que corrige la colisión visual del centro de la dona, pero 
     provoca desfase si la pantalla posee escalado por el hardware de pantalla o 
     zoom activo en el navegador, pudiendo verse la burbuja hasta 50px corrida 
     del cursor físico del mouse.

* Impacto Humano/Diseño: 
  Ralentización general y flickering molestos al redimensionar pantallas en 
  laptops convencionales.

8. ANTI-PATRONES DE ESTRUCTURA ("AI-Slop" y la Monolitización de App.tsx)
================================================================================
* Dónde ocurre: Enrutador Principal, Gestión de Estados de Firebase y App.tsx.
* Tipo de falla: Deuda Técnica de Mantenibilidad.

* Detalle del problema:
  La arquitectura declara que se rige por "Screaming Architecture", aislando los 
  componentes principales en módulos independientes (`activities`, `technicians`, 
  `dashboard`). Pero, por el afán del autómata I.A. de programar de forma reactiva 
  e inmediata para resolver hilos de conversación:
  1. El archivo principal `src/App.tsx` posee ya más de 2400 líneas de código.
  2. Concentra casi la totalidad de la lógica CRUD de base de datos de actividades, 
     personal, reportes, logs, gestión de nómina, estados globales del mapa, 
     notificaciones y control de contraseñas.
  3. Esto vulnera el principio de responsabilidad única (Single Responsibility Principle). 
     Cualquier modificación pequeña en la lógica del login puede alterar o corromper 
     accidentalmente componentes lejanos de viáticos, depósitos, histórico o reportes 
     en Excel debido al gigantesco alcance global del archivo.

RECOMENDACIONES DE MITIGACIÓN Y HOJA DE RUTA FUTURA:
================================================================================
1. migración a Firebase Admin SDK (Backend): Crear una Cloud Function robusta para 
   el registro, edición y desactivación física del personal. Así, al desactivar 
   un técnico, el backend de forma segura e inmediata anula su cuenta de acceso, 
   previniendo intrusiones.
2. Flexibilidad UX de Formulario: Reemplazar el input estricto por un sistema 
   de máscaras inteligentes (ej. auto-colocar el guion de celular a medida que se 
   escribe) y admitir números internacionales o fijos CANTV.
3. Descomprimir App.tsx: Dividir las funciones (`handleAddTechnician`, `handleDelete`, 
   `handleEditTechnician`) en sus respectivos contenedores de servicio dentro de 
   sus carpetas de módulo (`src/modules/technicians/services/technicianService.ts`), 
   reduciendo el tamaño de App.tsx a menos de 400 líneas enfocadas únicamente 
   en rutas y layouts globales.
